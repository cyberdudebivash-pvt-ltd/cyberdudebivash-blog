# REPORTX Phase 1 — Capability Reconciliation Matrix

**Date:** 2026-08-19
**Method:** Direct source-code inspection of all three report-generation systems this repository actually contains, cross-referenced against every prior certification record in `docs/audits/` and the repo root. Every row is grounded in a file path (and, where a claim is about *behavior* rather than *presence*, a real-data test run). Nothing below is inferred from a module or function name alone.
**Purpose:** Per the P0 continuation mandate's Section 4 — determine what genuinely needs to be built, as opposed to what the original prompt assumes should exist. This matrix is the deliverable that makes that determination auditable.

## 1. State classification used below

`COMPLETE_AND_PRODUCTION_WIRED` · `IMPLEMENTED_NOT_WIRED` (a.k.a. "certified but dormant") · `PARTIALLY_IMPLEMENTED` · `SCHEMA_ONLY` · `TEST_ONLY` · `NOT_IMPLEMENTED` · `BLOCKED_EXTERNAL_DEPENDENCY`

## 3. Real-data proof this session's wiring is genuinely live (not merely present)

Two representative articles were run through the actual, non-mocked `AuthorityTransformer.transform()` — a clean CVE (`cve_advisory` family) and a ransomware victim claim (`ransomware_claim` family), the same two families `report_contract.py` has a reconciled applicability matrix for.

**CVE article** — `product_tier: "TACTICAL"`, reason: `"2/14 mandatory sections withheld for insufficient evidence: key_judgements, intelligence_gaps"`. `evidence_graph`: 1 source, 5 evidence records, 5 claims, including `c-cve-id` at `status: "CONFIRMED"` (NVD is authoritative for its own ID assignment) and `c-exploitation-status` at `status: "UNKNOWN"` (this record's evidence doesn't confirm exploitation — never inferred from CVSS alone, matching mandate Section 17's explicit prohibition).

**Ransomware claim** — `product_tier: "TACTICAL"`, reason: `"3/14 mandatory sections withheld for insufficient evidence: key_judgements, business_impact, intelligence_gaps"`. `evidence_graph`: 4 claims, including `c-victim-claim` (`status: "REPORTED"`, text: *"A leak-site listing names this organization as a victim..."* — never `CONFIRMED`, matching the mandate's Section 18 boundary exactly) and `c-actor-attribution` naming the real actor.

Both results were re-derived by hand against `report_contract.py`'s actual applicability matrix before running (14 mandatory sections for each family; only Key Judgements/Intelligence Gaps — and, for ransomware, Business Impact — have no implementation anywhere in this pipeline) and matched exactly. This also independently reconfirms `docs/audits/REPORTX-24-SECTION-LONG-FORM-RELEASE-CERTIFICATION.md`'s own finding that no real report reaches `PREMIUM_LONG_FORM` today — now proven through the live wiring, not only through that document's own mocked/reconstructed tests.

## 4. Real defect found and fixed during this session's real-data testing

`discovery_bridge.py`'s ransomware-claim actor attribution (`build_claims()` and, identically, `build_threat_product()`) derived the actor name from `next(label for label in article.labels if label != "ransomware")` — **`article.labels` carries site taxonomy tags every article gets** (this repository's own `"CYBERDUDEBIVASH"` brand label, `"Threat Intelligence"`, etc.), not actor names. The canonical, already-sanitized field is `article.ransomware_group` (established by the Phase 1 `related_intelligence[]` slice, and already correctly used by `internal_linker.py`, `report_renderer.py`, and `analytical_depth_gate.py::_resolve_actor_context()`) — `discovery_bridge.py` was the one caller in the whole pipeline still reading the wrong field.

This was invisible before this session because nothing consumed `graph.claims`/`build_threat_product()`'s output in production — the exact "capability exists but the public report never benefits from it" defect class the P0 mandate's Section 6 names directly, and here it hid a real correctness bug, not just dead weight. In this session's own test article the bug surfaced as: attributing a ransomware claim to **"CYBERDUDEBIVASH"** (this site's own brand) instead of the real actor. Fixed by reading `article.ransomware_group`, with the same `"Unknown Group"` placeholder guard already established in `internal_linker.py`/`report_contract.py` (a third, deliberate copy — this file already keeps itself dependency-light from the other two, per its own header comment). Two new regression tests added (`test_actor_attribution_uses_ransomware_group_not_the_site_taxonomy_label`, `test_unknown_group_placeholder_does_not_become_a_named_actor_attribution`); full engine suite re-run clean (929/930 — the one failure is pre-existing and unrelated, see §6).

## 5. Highest-leverage next increment (named, not implemented this session)

**Wire `contradiction_engine.py` into `discovery_bridge.py`/`pipeline_composer.py`.** Every claim now reaching production carries a real (currently always-empty) `contradictions: list[str]` field, and `contradiction_engine.py` (144 lines, its own test file `test_contradiction_engine.py`) already exists to populate it — but nothing calls it. This is the identical "certified/implemented but dormant" pattern this session closed for `analytical_depth_gate.py`/`report_contract.py` and for the evidence graph itself, and it is the mandate's own next-named phase (1D, immediately after the claim graph this session wired). Not attempted this session because it deserves the same full rigor (real conflicting-evidence test data, adversarial testing against the "manufactured consensus" failure mode Section 10 of the mandate specifically forbids) rather than a rushed pass appended to an already-substantial diff.

**Runner-up:** rendering `evidence_graph`'s claims into the actual public HTML body (today they are computed and now *observable in logs/return values*, but the rendered report still only shows the composer's existing narrative summary paragraph, not a claim-by-claim ledger). This is a content/UX decision (how much of the graph belongs in a public-facing report vs. an internal/API-only artifact) that the existing `docs/audits/REPORTX-24-SECTION-LONG-FORM-RELEASE-CERTIFICATION.md` deliberately deferred for the same reason, and this session did not revisit that judgment.
