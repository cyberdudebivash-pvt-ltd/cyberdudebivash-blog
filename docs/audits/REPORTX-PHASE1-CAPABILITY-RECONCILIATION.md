## 3. Real-data proof this session's wiring is genuinely live (not merely present)

Two representative articles were run through the actual, non-mocked `AuthorityTransformer.transform()` — a clean CVE (`cve_advisory` family) and a ransomware victim claim (`ransomware_claim` family), the same two families `report_contract.py` has a reconciled applicability matrix for.

**CVE article** — `product_tier: "TACTICAL"`, reason: `"2/14 mandatory sections withheld for insufficient evidence: key_judgements, intelligence_gaps"`. `evidence_graph`: 1 source, 5 evidence records, 5 claims, including `c-cve-id` at `status: "CONFIRMED"` (NVD is authoritative for its own ID assignment) and `c-exploitation-status` at `status: "UNKNOWN"` (this record's evidence doesn't confirm exploitation — never inferred from CVSS alone, matching mandate Section 17's explicit prohibition).

**Ransomware claim** — `product_tier: "TACTICAL"`, reason: `"3/14 mandatory sections withheld for insufficient evidence: key_judgements, business_impact, intelligence_gaps"`. `evidence_graph`: 4 claims, including `c-victim-claim` (`status: "REPORTED"`, text: *"A leak-site listing names this organization as a victim..."* — never `CONFIRMED`, matching the mandate's Section 18 boundary exactly) and `c-actor-attribution` naming the real actor.

Both results were re-derived by hand against `report_contract.py`'s actual applicability matrix before running (14 mandatory sections for each family; only Key Judgements/Intelligence Gaps — and, for ransomware, Business Impact — have no implementation anywhere in this pipeline) and matched exactly. This also independently reconfirms `docs/audits/REPORTX-24-SECTION-LONG-FORM-RELEASE-CERTIFICATION.md`'s own finding that no real report reaches `PREMIUM_LONG_FORM` today — now proven through the live wiring, not only through that document's own mocked/reconstructed tests.

## 4. Real defect found and fixed during this session's real-data testing

`discovery_bridge.py`'s ransomware-claim actor attribution (`build_claims()` and, identically, `build_threat_product()`) derived the actor name from `next(label for label in article.labels if label != "ransomware")` — **`article.labels` carries site taxonomy tags every article gets** (this repository's own `"CYBERDUDEBIVASH"` brand label, `"Threat Intelligence"`, etc.), not actor names. The canonical, already-sanitized field is `article.ransomware_group` (established by the Phase 1 `related_intelligence[]` slice, and already correctly used by `internal_linker.py`, `report_renderer.py`, and `analytical_depth_gate.py::_resolve_actor_context()`) — `discovery_bridge.py` was the one caller in the whole pipeline still reading the wrong field.

This was invisible before this session because nothing consumed `graph.claims`/`build_threat_product()`'s output in production — the exact "capability exists but the public report never benefits from it" defect class the P0 mandate's Section 6 names directly, and here it hid a real correctness bug, not just dead weight. In this session's own test article the bug surfaced as: attributing a ransomware claim to **"CYBERDUDEBIVASH"** (this site's own brand) instead of the real actor. Fixed by reading `article.ransomware_group`, with the same `"Unknown Group"` placeholder guard already established in `internal_linker.py`/`report_contract.py` (a third, deliberate copy — this file already keeps itself dependency-light from the other two, per its own header comment). Two new regression tests added (`test_actor_attribution_uses_ransomware_group_not_the_site_taxonomy_label`, `test_unknown_group_placeholder_does_not_become_a_named_actor_attribution`); full engine suite re-run clean (929/930 — the one failure is pre-existing and unrelated, see §6).

## 5. Highest-leverage next increment (named, not implemented as of Round 2)

**Superseded (Round 1's pick, done in Round 2):** wiring `contradiction_engine.py` — see §7.1.

**Current pick: Key Judgements.** This is the mandate's own repeated, explicit "biggest blocker for PREMIUM_LONG_FORM," and Round 2 investigated it far enough to say precisely why it wasn't attempted: `_build_analyst_prompt()` (`authority_transformer.py`) — the actual prompt sent to Groq/DeepSeek/OpenRouter/Anthropic — has **no "Key Judgements" section at all** in its template (confirmed by direct read: its 21 requested sections are Executive Summary, Verified Facts, Threat Classification, Threat Severity Assessment, Business Impact, Technical Analysis, CVE Analysis, MITRE ATT&CK Mapping, IOC Intelligence, Detection Engineering Guidance, Sigma Rules, Threat Hunting Queries, SOC Analyst Playbook, Executive Decision Matrix, Executive Recommendations, MSSP Opportunities, Sentinel APEX Intelligence Correlation, AI Security Impact, Predictive Intelligence, Long-Term Strategic Risk, References — none of them Key Judgements). So even a fully-succeeding LLM call today could never populate this section; the gap is upstream of provider reliability entirely. Two things would be required together: (1) extend the prompt template with a Key-Judgements ask shaped to the mandate's own contract (judgement/confidence/evidence_refs/claim_refs/reasoning_basis/decision_relevance/limitations/what_would_change_the_judgement), and (2) a parser mapping the LLM's free-text response back to real `evidence_graph` claim IDs so `evidence_refs`/`claim_refs` are genuine, not fabricated placeholders. **Not attempted this session** because this sandbox has no real LLM API keys/network access to verify how an actual provider responds to a modified prompt — editing a live-tuned, already-carefully-worded production prompt template without being able to test it against a real model would be exactly the kind of unverified change CLAUDE.md's Architecture Preservation Rule and this mandate's own "never fabricate test execution" rule both prohibit. This is the one item in this document classified `BLOCKED_EXTERNAL_DEPENDENCY` in the strict sense (not merely large) — a founder/owner call with live-canary access is the correct next actor, not a further code-only session.

**Runner-up (unchanged from Round 1):** rendering `evidence_graph`'s claims into the actual public HTML body as a claim-by-claim ledger, rather than the composer's existing narrative-summary paragraph. Still a content/UX decision this document does not make unilaterally.

## 7. Round 2 additions (Phase 1D, 1E, provider reliability, artifact binding)

### 7.1 Contradiction engine — now wired

`contradiction_engine.py`'s two checkers (dimension-level `EpistemicState` conflicts via `find_dimension_contradictions()`; rendered-text pattern conflicts via `find_text_contradictions()`) now run unconditionally inside `compose_report()` (`pipeline_composer.py`) against the real evidence graph and the real rendered HTML, surface as `result["contradictions"]` in `transform()`'s output, and hard-block publication in `validate_publication()` on any `severity=="block"` finding — every contradiction this engine can currently construct, by its own module-docstring design ("Gate: unresolved_contradictions == 0").

**Honest limitation, proven not assumed:** the dimension-level layer cannot yet find a real conflict, because `discovery_bridge.py` never builds two competing claims for the same canonical dimension within one article (single-source construction; an independent-source match upgrades an existing claim's `corroboration_state` rather than adding a second, competing claim — see `_apply_independent_corroboration()`'s own docstring). `_dimension_tags_for()`'s 1:1 claim_id→dimension mapping makes this structurally provable, not merely untested: verified via 4 real-article tests (`TestDimensionTagsFor`) plus 2 zero-contradiction real-article tests (`TestContradictionWiring`), all passing. The wiring is real and load-bearing anyway — it engages automatically the moment a future increment adds cross-source claim merging, without a second wiring pass, and the text-pattern layer is already live against whatever real prose `compose_report()` renders today.

### 7.2 Analytical confidence — 3-axis structure exposed

`executive_products.py`'s `source_reliability_grade()`/`information_credibility()`/`overall_analytical_confidence()` were already computed and rendered as 3 distinct prose lines before Round 2 (discovered mid-session: `test_rendered_report_shows_three_separate_labeled_reliability_lines` already existed and passed pre-Round-2). Round 2's addition is exposing the same 3 real values as `result["analytical_confidence"]` structured data for the first time, cross-checked against the rendered prose in the same test.

**Genuinely absent, not attempted:** `assumptions[]` as a distinct analytical concept (mandate Section 14 / new-mandate Section 4). Confirmed by repository-wide grep (`class Assumption|assumptions\[|ASSUMPTION`) returning zero hits anywhere in `Sentinel-APEX/`. Building this from scratch — genuine assumption *identification*, not just a new empty list — is new analytical capability, not wiring, and was not attempted this round.

### 7.3 Provider reliability — bounded 429 retry, real backoff/jitter/Retry-After

`llm_client.py` had **zero** retry/backoff/jitter/`Retry-After` handling before Round 2 — confirmed by full-file read: every exception, 429 and 402 alike, immediately moved to the next provider. Now `_call_openai_compat()` retries specifically on HTTP 429 (bounded: 2 retries, ≤10s each, honors a real `Retry-After` header when the provider sends one, else exponential backoff with jitter), and continues to never retry 402 or any other error — matching the live-canary evidence in `PHASE-0-RELEASE-CERTIFICATION.md` exactly (Groq succeeds then 429s within seconds; DeepSeek/OpenRouter 402 on account billing, not retryable). Bounded deliberately against the triggering workflow's real 5-minute ceiling and up-to-5-posts-per-run volume (`PRODUCTION-PIPELINE-AS-IS.md` §2.5). 13 new tests, all using dependency-injected `sleep_fn` so the suite verifies real backoff-timing logic without a single real sleep (full run: 0.20s for 28 tests).

**Not independently re-verified against live Groq/DeepSeek this session** — this sandbox has no configured provider API keys or outbound network access to those endpoints. The mechanism is proven correct via HTTP-mock-level tests (status codes, headers, call counts) reproducing the exact conditions Phase 0's own live canary observed, not via a fresh live call.

### 7.4 Certified artifact hash binding

`report_integrity.compute_artifact_hash()` (SHA-256 of the exact certified HTML) is computed inside `transform()` immediately after `validate_publication()` passes and returned as `result["certified_artifact_hash"]`. `main.py::run_pipeline()` recomputes the same hash over the exact `transformed["content"]` about to be sent to Blogger, immediately before the `publish_post()` call, and raises the existing `PublicationIntegrityError` (no new exception type, no new retry-queue path — reuses what's already there) on any mismatch.

Verified two ways: (1) code trace confirms `transformed["content"]` is never mutated between `transform()`'s return and the publish call today, so this is provably a no-op currently — the same "safe because unreachable today, protective the moment it becomes reachable" pattern as the FLASH and contradiction gates; (2) a real end-to-end adversarial test (`test_certified_artifact_hash_mismatch_blocks_publication`) runs the actual `run_pipeline()` with a deliberately tampered hash and confirms `publisher.publish_post()`'s endpoint is never called, `published == 0`, and every article is recorded `integrity_blocked`.
